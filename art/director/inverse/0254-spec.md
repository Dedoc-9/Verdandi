## 1. The defect as measured

### 1.1 Where it is (ESTABLISHED, read at 7dee210)

`apply_revision` (art/director.py:294-330) is the only place the revision language is applied and the only place an inverse is made. Rows are `text.split("\n")`, never `splitlines`.

- **`=`** rewrites the keyed row as `" ".join(body.split())`, plus `"  #" + comment` when the row has one. It records `"= " + old_code.strip()`. The record keeps inner spacing, but applying it collapses that spacing. Leading and trailing whitespace and the comment's spacing are lost.
- **`+`** pops every trailing empty row, appends `[stmt, ""]`, and records `"- " + key`, whatever the parent's tail.
- **`-`** deletes the row and records `"+ " + code`. That record applies at the end of the file, without the row's comment.

The list of records is reversed. The stored inverse is the admit event's field `inverse`, computed in `admit_checks` (director.py:927) from `ws.text()`, which reads CR LF as LF.

Replay applies only the forward revision, and discards the inverse it computes (`_inv`, director.py:1086). It reads a stored `inverse` only to check that a later undo's revision equals it (director.py:1076-1081). Nothing ever checks a stored inverse against anything else.

## 2. The inverse form

### 2.1 Three inverse-only forms (DECLARED)

**Definitions.**
- A **row** is one element of `text.split("\n")`, where `text` is `Workspace.text()`: the brief's UTF-8 bytes with CR LF read as LF. A row never holds LF. It may hold any other character, CR included.
- A **position** is a 0-based index into that list. It is taken at the moment of the revision line that records it, after the lines before it have been applied. It is never dress's 1-based `line`, which counts `splitlines` rows. Positions taken in the parent are wrong: they restore only 2,485 of 4,970 two-`-` pairs on foundry-yard (MEASURED, `census/variant.py`).
- `KEY(x)` is apply_revision's `keyed` (the statement key of `x.split("#",1)[0]`), or none.

**Syntax.** Each form is the two characters `@=`, `@+` or `@~`, exactly one space, then the VERDANDI-CANON 0 bytes (art/director/intent.py `dumps`) of one array. In that array:
- integers are strings matching `0|[1-9][0-9]{0,18}`;
- a row is a string that holds no LF;
- `false` is allowed only as `@+`'s third field;
- there is no null.

| form | array | applies as | guard (otherwise `INTENT-APPLY`) | its own inverse |
|---|---|---|---|---|
| `@= [I, W, R]` | the position; the row the admission wrote; the row to restore | `rows[I] := R` | `I < len(rows)`; `rows[I] == W`, byte for byte; `KEY(W)` and `KEY(R)` both defined and equal | `@= [I, R, W]` |
| `@+ [I, R, S]` | the position; the row to restore; the row that stood at `I` once it was gone, or `false` when it was the text's last row | `rows.insert(I, R)`, or `rows := [R]` (the third arm) | `KEY(R)` defined; no row has `KEY(R)`; and one of: (i) `S` is `false` and `I == len(rows)`; (ii) `S` is `false`, `I == 0` and `rows == [""]`, the empty child, in which case `rows := [R]`; (iii) `I < len(rows)` and `rows[I] == S` | `- KEY(R)` |
| `@~ [A, B]` | trailing empty rows found; trailing empty rows to leave | the last `A` rows removed, then `B` empty rows appended | the rows end in exactly `A` empty rows | `@~ [B, A]` |

Arm (ii) exists because a forward `-` can leave `rows == []`, whose text `""` reads back as `[""]`. Without arm (ii) the undo over that child is refused. MEASURED by the red team with the spec's model: 768 refusals in 200,000 fuzzed cases, every one with child `""`. Arm (ii) cannot misfire on an honest record: an honest `@+` meets `[""]` with `S` false and `I == 0` only at that boundary. With arm (ii), 0 refusals and 0 inexact in 20,000 fuzzed cases (MEASURED, `refute-alldel/p.py`). The forward is unchanged; a child `""` is still refused by the exporter (ART-REFUSED), so the arm only makes T-0254 total.

The key check in `@=` never refuses an honest record, redo included. An `=` finds its row by that key, and W's code is the body that carries it. It is defence in depth against a forged record; the replay check (§2.5) is what refuses forged records.

**What each forward op records.** The forward ops are unchanged byte for byte (§4.1); only their records change.
- **`=` at row `I`** records `@= [I, the row as rewritten, the old row verbatim]`.
- **`-` of row `I`** records `@+ [I, the row verbatim, the row that followed it]`. The third field is `false` when the deleted row was the last row of the list.
- **`+`** records `- KEY` when it removed exactly one trailing empty row, that is, when the parent's rows ended in exactly one empty row. That is today's record, byte for byte. When it removed `K ≠ 1`, it records `- KEY` followed by `@~ ["1", "K"]`.

The stored `inverse` is each line's group, concatenated in reverse line order, each group in its own order. Every arm of this table was MEASURED by the scratch model (`spec254/model.py`, §5), except arm (ii) and the key check of `@=`. Arm (ii) was measured by the red team's variant of the model. The key check is DECLARED; it holds for honest records by the argument above.

### 2.3 How the inverse is stored, and what marks its era

The inverse is stored in the admit event's existing field `inverse`, a list of strings, as today. No field is added and none is renamed. The event stays DIRECTOR-0 version 0.

Which inverses mark their era:
- An inverse holding a line beginning `@` is 0254's. No 0254 inverse holds a line beginning `= ` or `+ `.
- An inverse holding a line beginning `= ` or `+ ` was recorded before 0254.
- **An inverse made only of `- KEY` lines does not mark its era.**
  - Under 0254 it is exact by construction, because a `+` whose parent did not end in exactly one empty row also records `@~`.
  - Before 0254, every `+` recorded a bare `- KEY` whatever the parent's tail. That record is exact only if every `+` ran on rows ending in exactly one empty row.
  - MEASURED with 7dee210's apply_revision (`rt-era/probe.py`, `rt-ptail/probe.py`). For `+ lamp b …` after `lamp a …` the inverse is `['- lamp b']` for the tails `""`, `"\n"`, `"\n\n"` and `"\n\n\n"`. It restores the parent only for `"\n"`. Two `+` lines on a `"\n\n"` parent give `['- lamp c', '- lamp b']`, which is not exact.
  - The exactness of such an inverse is known only from the two replays of the restoration verdict (§4.2).

### 2.4 How undo applies it

**One predicate.** `inverse_of_ok(events, i, it, before)` replaces the two copies of today's test, `admission_evidence` (director.py:844-847) and replay's `inv_ok` (1078-1081). It requires:
- `int(i) < before`;
- `events[i]` is an admit event;
- `list(events[i]["inverse"]) == list(it["revision"])`;
- `it["layout"] == []`.

`before` is `len(events)` at evaluation and at admission, and `int(ev["seq"])` in replay. Without the bound, an undo could name a later admission whose recorded inverse is equal, such as its own redo (MEASURED, `rt254x/t6.py`).

**One enforcement point for "only by undo".** `apply_revision(text, lines, undo=False)` raises `IntentError("INTENT-INVERSE-ONLY")` for any `@` line unless `undo` is True. No caller adds a second refusing layer for that rule. Each caller maps that one IntentError to its own refusal where it applies:
- **evaluation**: a REFUSED verdict;
- **admission**: `SystemExit "REFUSED (INTENT-INVERSE-ONLY): …"`;
- **replay**: `LedgerError LEDGER-INVERSE-ONLY`.

A plant can then switch off the effective layer (§8).

**The studio.**
- `Gateway._undoing` builds the undo intent from `list(a["inverse"])`, verbatim, as today. It calls `D.evaluate_doc(ws, it, undo_of=a["seq"])`.
- `evaluate_doc(undo_of=N)`:
  1. replays `events[:N+1]`, so a forged stored inverse is refused before anything is applied (§2.5, LEDGER-INVERSE);
  2. holds `inverse_of_ok(events, N, it, len(events))`, and returns REFUSED `INTENT-INVERSE-ONLY` otherwise;
  3. only then calls `apply_revision(ws.text(), it["revision"], undo=True)`.
- A LedgerError raised by that replay is mapped in `_undoing` through `director_refusal`. It is answered STUDIO-DIRECTOR-REFUSED with the director's code, as a ledger that does not read is answered today (studio.py:2258-2260), and nothing is appended.
- The press then continues as today: `append_evaluation`, then `_inverse_clean` (CLEAN only, else STUDIO-NOT-UNDOABLE), then `cmd_admit(..., inverse_of=a["seq"], gate=...)`. The dry account (`admit_dry`) runs the same checks.

**The admission.** `admit_checks` keeps its order, with one change: at director.py:927 it applies `apply_revision(ws.text(), it["revision"], undo=inverse_ok)`. That comes after the verdict check, after `contract.missing` and before any write. As a result:
- an undo without a still still answers ADMISSION-0 "no still of the candidate";
- an undo naming the wrong admission still answers ADMISSION-0 "not that admission's exact inverse";
- only an `@` evaluation admitted with a still and without `inverse_ok` reaches `REFUSED (INTENT-INVERSE-ONLY)`.

**Replay** sets `inv_ok` afresh for every admit event, before anything is applied, so nothing carries over from an earlier event:
- `inv_ok` is `inverse_of_ok(events, evidence.inverse_of, it, int(ev["seq"]))` when the admitted evaluation has a record and the evidence names `inverse_of`;
- otherwise it is False. That covers a record-less admission from before 0222, and plaza-night's #9, #11 and #13 are three of these (MEASURED).

If the spec's line were implemented literally, with `inv_ok` bound only inside `if "record" in src`, plaza-night's replay would raise `UnboundLocalError` at #9 (MEASURED in memory, `refute-invok/literal.py`). With a value carried over from a recorded undo, a later record-less `@` admission would apply (MEASURED with stubs, `refute-invok/stale.py`).

After LEDGER-ADMIT, LEDGER-STALE, LEDGER-VERDICT and LEDGER-EVIDENCE, in today's order, replay applies `apply_revision(st["art"], it["revision"], undo=inv_ok)`. An `INTENT-INVERSE-ONLY` there is `LedgerError LEDGER-INVERSE-ONLY`. The plant row "plant: an admit event written past the director, with no evidence" therefore still answers LEDGER-EVIDENCE.

**CERT-0's check** (`certificate.check`) applies a recorded inverse in memory with `undo=True`. It reaches only inverses whose ledger has replayed, comparison included (§2.5). Its callers are `_certificate_of` and `recover_certificates`, which replay `events[:i+1]` first. A kept certificate counts as its event's own only if its `inverse.revision` equals that event's `inverse`, besides `seq` and `event_sha256` (`_kept_is_own`, studio.py:2433). The command `python art/certificate.py check` reads the brief by Workspace.text()'s rule, `open(path, "rb").read().replace(b"\r\n", b"\n").decode("utf-8")`, never in text mode (certificate.py:189 opens it with universal newlines today).

### 2.5 The guard, and the stored inverse's check

**The stored inverse is checked against the one its revision makes.** In replay, for every admit event whose stored `inverse` holds an `@` line, `list(ev["inverse"]) == list(_inv)` is required. `_inv` is the inverse apply_revision computes there under the same `undo` flag. Otherwise replay raises `LedgerError LEDGER-INVERSE`: "#N's stored inverse is not the one its revision records over the text it was admitted on".

- Inverses with no `@` line (pre-0254, and 0254's pure `- KEY`) are not compared, so old ledgers replay as they are. An unconditional comparison would refuse the committed ledger: its #9, #11 and #13 hold statement-form inverses that 0254 would record as `@` lines (MEASURED, `refute-replayinv/probe.py`).
- `held_head` and `cmd_verify` go through replay. So the check also runs at every append, at the commit's fence, and in Import's staging (IMPORT-LEDGER carrying the code). It runs before `evaluate_doc(undo_of)` applies anything (§2.4).
- MEASURED at 7dee210: a ledger with #9's inverse replaced by `['= lamp zz 1,2,3 100 1']` and its chain recomputed replays, chains and reads today.

**The guard, form by form.** Each record checks, at its own moment, what the table in §2.1 says. A failed guard raises `INTENT-APPLY`, an existing code, naming the form, the position and what it found. It never falls back: no `@=` or `@+` is retried by key, and the studio never retries an undo in another form.
- `@=` guards the row it wrote, and the key of the row it restores.
- `@+` guards the absence of its key, and its successor row or the end of the text. The successor is not the admission's own row, so `@+` also refuses edits and shifts that leave the admission's row alone.
- `- KEY` has no positional guard. It is a key search, found exactly once. It is the inverse of every `+` (today's record, kept by the ruling, which gives `+` only "the trailing blank lines") and the redo of every `@+`.
- `@~` guards only the count of trailing empty rows.

**What the guard is not.** It is not a check that the whole text is the admission's child. A whole-child refusal was considered and is excluded by the frozen contract (ESTABLISHED, read):
1. The plant run of 0253-matrix.json's row M13u is pinned `"answer": "undone"`, `"ledger": "+2"`, `"brief": "changed"`. In that run the binding check is removed, another canopy is edited in place, and the edit is rebased.
2. Its honest run is pinned BINDING-MISMATCH, and v0's case B2 answers the undo "REFUSE BINDING-MISMATCH (the undo has no stale check; the binding answers it)".

A whole-child check placed before the binding check would answer both with STUDIO-NOT-UNDOABLE and change frozen answers.

## 3. Who may write and apply it

**Only undo.** An `@` line is built by the host, from the ledger (`a["inverse"]`, checked as in §2.5). It is applied only when `inverse_of_ok` holds. 1. write an intent whose revision is the admit event's `inverse`;
2. `evaluate BRIEF FILE --inverse-of N`;

**Grammar.** VERDANDI-INTENT 0's revision rule widens in both twins: art/director/intent.py `validate` (209-211) and art/director/conform.rs `validate` (544-549). A line is valid if it is either:

- `@=`, `@+` or `@~`, then exactly one space, then a rest that is ASCII, is its own canonical bytes, and has the array shape of §2.1 with no row holding LF.

## 5. The theorem (T-0254)

**Statement.** Let `P` be any parent text (a `str` with no lone surrogate) and `r` any revision of ordinary lines that `apply_revision(P, r)` accepts, with `(C, I) = apply_revision(P, r)`. Then:
1. `apply_revision(C, I, undo=True)` returns `P`, byte for byte, with an inverse `I'`;
2. `apply_revision(P, I', undo=True)` returns `C` (the redo).

The same holds for a revision of `@` lines applied under `undo=True` to the text it was recorded over.

**Conditions.**
- **(c1)** The inverse is applied to `C` itself: the admission's child.
- **(c2)** The inverse is the one `apply_revision` computed at the admission, and its lines reach `apply_revision` unchanged. For a stored inverse holding an `@` line, replay enforces this (LEDGER-INVERSE, §2.5). The canonical form round-trips every row. The studio and the command line pass `inverse` verbatim.
- **(c3)** "Byte for byte" is of the LF-read text that `art_sha256` hashes. A brief stored with CR LF line endings is rewritten in LF by the admission.
  - A child holding `"\r\n"` in its text (a row other than the last ending in CR) is written as CR LF bytes, which Workspace.text() reads back as LF. Such a child arises from disk bytes CR CR LF, from a comment tail ending in CR that `=` keeps, or from a `+` after a last row ending in a lone CR.
  - Then the files are not the head the ledger records, and every later press is LEDGER-UNLOGGED. This is a defect of the forward write, as at 7dee210, and 0254 does not repair it (§9).
  - MEASURED: `rfcr/t.py`, `t2.py`. Over a parent whose last row ends in a lone CR and has no final LF, `=` and `-` give children that read back exactly. Only `+` fails.

**Corollary** (one way only).
- **When the undo applies to the child.** In the studio an undo is admitted only over files whose head is the ledger's head: `held_head` runs under the content lock at `append_evaluation`, and the commit reads the head again. So (c1) holds whenever the art the ledger replays to at the press is the admission's child `C` and `"\r\n" not in C`.
- **What keeps (c1).** In particular, it holds when no event that changes the art (an admission, or a rebase recording another art text) lies between the admission and the press. Events that leave the art as `C` do not break (c1): an exporter or map rebase, a rebase that records nothing new, an evaluation or approval, or another admission followed by its own exact undo.
- **When the verdict is exact.** The restoration verdict is `exact` when, in addition, the files' head at the press is the admission's `head_after`, that is, their world and exporter parts equal its `parts_after`. The undo's head is then the admission's `head_before`.
- **The converses do not hold.** An exporter rebase in between leaves (c1) and the art's bytes intact, yet the undo answers `not-restored ['exporter']` (STUDIO's "literal case" row, art/page_dash.py:295-314). Conversely, `exact` is a sufficient claim only: a `+` whose added row was edited and rebased is undone to the parent and reads exact (§2.5).
- **If `"\r\n" in C`**, every later press is LEDGER-UNLOGGED. After a rebase, the undo applies over `C.replace("\r\n","\n")` and is reported not exact (MEASURED: P=`…1\r`, `+` gives a back of `…1`).

**Argument.** Let `rows_0 = P.split("\n")`, and let `rows_j` be the rows after line `j`. Each line's group, applied to `rows_j`, gives `rows_{j-1}`, and its guards hold there by construction:
- `@=` finds the row it wrote, and its two keys are the `=` line's key.
- `@+` finds its key absent, because `-` required exactly one row of that key. It finds its successor at `I`, or the end, or, when the forward left `rows_j == []` (read back as `[""]`), its third arm.
- `- KEY` finds exactly one row of the key `+` added.
- `@~ [1, K]` finds exactly one trailing empty row once `- KEY` has removed the appended statement.

Applying the groups in reverse walks `rows_n` back to `rows_0`. `"\n".join` and `split("\n")` are mutually inverse on non-empty lists of LF-free strings. The one empty list, `rows_n == []`, is read back as `[""]` and handled by arm (ii). The same per-step argument covers the `@` forms' own inverses, which gives the redo.

**Grade.**
- **Now: DECLARED.**
- **Measured so far.**
  - The scratch model of this syntax, without arm (ii) and the key check, is exact and its redo is exact on 6,768 of 6,768 single and 89,311 of 89,311 multi-line applied cases. Its forward step equals 7dee210's in every case, and every recorded line is valid under §3's grammar (MEASURED, `spec254/model.py`, 70.4 s).
  - A variant with arm (ii) has 0 refusals and 0 inexact in 20,000 fuzzed cases, including empty children (MEASURED by the red team).
  - The key check is not measured; it is DECLARED from the argument in §2.1.
  - These are models, not the repair.
- **After commit 2:** MEASURED on the built `apply_revision` by the frozen vectors and the census re-run, and ESTABLISHED by reading the argument against the code.
- **Never claimed:** a proof for every `P` beyond that reading. One author wrote the model and the specification; the vectors marked "by hand", and the children anchored to 7dee210 (§6.3), are what stand against a shared mistake.

**Falsifier.** Any of the following falsifies T-0254:
- an accepted `(P, r)` whose undo over `C` is not `P`, or whose redo is not `C`;
- a guard that passes over a text where its position does not hold what it records;
- a forward child that differs from 7dee210's;
- a stored `@` inverse differing from its revision's that replays.

The plant `inverse-parent-positions` (positions taken in the parent) must fail EX4.

**What T-0254 does not state.** That an undo over a world that moved restores anything. Such an undo is refused where a recorded position or the stored row moved; otherwise it is applied and reported.

## 8. The test matrix to freeze (`0254-matrix.json`)

**The rule, per suite.** Each list is ordered as its suite prints it, and the rule applies within that list only.

## 9. What 0254 does not show

- **Undo over a moved world.** It does not make such an undo restore anything. It refuses where a recorded position or row moved. Otherwise it applies and reports. v0 binds the scene at the press, never the child's head, and that is unchanged.
- **`+`'s undo.** It is a key search. Under OPEN-1(i), a rebase of the added row is discarded and the verdict reads `exact` (GD12).
- **The forward ops.** Their defects stay byte for byte:
  - a lone CR, VT, FF, FS, NEL or LS joining rows lets `=` drop a statement;
  - `=` single-spaces the code it writes;
  - a child holding `"\r\n"` is written as CR LF and does not read back, so later presses are LEDGER-UNLOGGED (§5 (c3)).
- **The two row models**: LF rows against `splitlines` statements.
- **The twins' disagreement on U+001C** in `validate`'s whitespace predicates on prompt and layout (MEASURED, Rust 65/66 on a probe vector).
- **Legacy inverses.** A pre-0254 `- mover` inverse is still undone to another scene under a `statements-not-bytes` label. A pre-0254 `- KEY`-only inverse does not say whether it is exact.
- **Authentication of the ledger.** The ledger is a keyless chain. A writer of its files can still forge a statement-form inverse, as at 7dee210, and can put any bytes in the world through a genesis's or a rebase's `art_text`. 0254 authenticates nothing against that writer. It refuses only a stored `@` inverse that is not its revision's.
- **The freeze against a coordinated edit.** A coordinated edit of a frozen file and its line in frozen-0254.jsonl is caught by none of 0254's checks, as is true of 0253 today. The classifier's loosenings name neither freeze.
- **The undo target recognised by its note** (OPEN-8).
- **The IntentError escape at the press** (OPEN-5).
- **A Rust twin of the application** (OPEN-4).
- **His own worlds.** NOT_MEASURED; so are Linux, any timing or feel, and anything the gate holds (no row is added or changed).
